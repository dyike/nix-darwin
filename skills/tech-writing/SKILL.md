# tech-writing

面向一线读者的中文写作方法。适用范围不限于技术文章：周报、汇报、复盘、方案同样适用，因为读者的需求是一样的——**在最短时间内知道发生了什么、为什么、我该怎么办**。

## 核心心智

写作不是介绍你做了什么，而是**替读者解决他此刻的问题**。读者的时间是最贵的资源。每句话都要能通过这一问：删掉它，读者会不会少知道一件事？不会，就删掉。

三条总纲：

1. **先给结论，再给推导**。读者随时可能停止阅读，把最有价值的信息放在他还没走的时候。
2. **具体压倒抽象**。数字、公式、代码、类比，都比形容词有信息量。
3. **敢下判断**。"我们不做 X，理由是 Y" 比 "X 需要根据实际情况权衡" 有用一百倍。

## 十条可操作的规则

### 1. 第一句就把话说完

不铺垫背景，不交代动机，直接给定义或结论。一句话定义 + 一句话预告结构，开场就结束。

写周报同理：第一句是"这周把 X 上线了，Y 卡在 Z"，不是"本周主要围绕 X 项目开展了以下工作"。

### 2. 问题在前，方案在后

先把读者会遇到的问题摆成一串，再逐条对上你的解法。读者读到方案时，才知道它值多少钱。

顺序错了，读者只能看到一堆特性；顺序对了，同样的内容变成了"原来这个坑我也踩过"。

### 3. 短回答先行

有明确问句的地方，用一行给答案，再展开。

> 我该用异步接口还是多开线程？
> 短回答：延时不高时先用简单易懂的同步接口，不行再用异步，只有需要多核并行计算时才自己开线程。

被问"这事什么时候能好"，先答"下周三"，再解释依赖。

### 4. 用数字，不用形容词

"性能很好"是零信息。给数字，最好给分位数：调度延时中位数 3 微秒，90% 在 10 微秒内，99.99% 在 30 微秒内——这才叫说清楚了。

汇报同理：不写"效率大幅提升"，写"构建从 8 分钟降到 90 秒"。凡是声称收益却给不出数字的句子，补数字，补不了就删掉。

### 5. 给读者一个能当场用的判据

最有价值的段落，是读者合上文档就能照做的。给公式、给阈值、给算式，并且**跟上两三个代入真实数字的算例**：

> 判断同步还是异步：算 qps × latency(秒)，和 CPU 核数同数量级就用同步。
> - qps=2000, latency=10ms → 20，和 32 核同数量级，同步。
> - qps=100, latency=5s → 500，不同数量级，异步。

公式 + 算例是这类写作的黄金结构。改进项也一样：不是"加强监控"，而是"P99 超过 200ms 报警"。

### 6. 类比要"可推导"，不是"听着像"

好类比能让读者自己推出下一步结论。比如把过载比作水池：入水量大于出水量，池子终将盛满；入水量降下来，一段时间后总会排空——读者立刻能自己想明白为什么单个服务不会产生雪崩。

用读者已有的知识做锚点，然后**立刻标出类比失效的边界**。类比不封边界就是误导。

### 7. 把"不做什么"和拒绝理由写出来

单列一节 NonGoals，每条跟一句**拒绝理由**。

写方案时列"本次不做的范围 + 为什么不做"；写周报时写"X 我没做，因为 Y 优先级更高"。写下拒绝理由，评审时能省掉一半来回。

### 8. 认真对待别人的方案，然后逐条说清为什么不够

不要用"业界方案不满足我们的需求"一句带过。把候选方案全列出来，承认各自的合理动机，再说清方案 1、2、3 分别死在哪，最后才轮到你选的那个。

**读者信任的不是你的结论，是你否决其他选项的过程。**

### 9. 承认局限、代价和不确定

坦白弱点提升可信度，不会降低。"这套逻辑非常复杂"、"理论上会死锁，但需要线程恰好在两条指令之间被换出，实践中很少出现"、"这个抽象不是万能的，否则就不需要下面那一层了"——这些话都该写进去。

必要时甚至该劝退自己的功能："我们不鼓励用户用这个类"。

汇报同样：主动说"这个方案在 X 场景下会退化"，比等着被问出来强得多。

### 10. 直接对读者说话

用"你"，可以反问，可以有态度：

> 你的场景中请求可丢可不丢、可处理可不处理，因为 client 根本无法感知——你真的确认这是 OK 的？

有态度不等于不严谨。每句刻薄话后面都得跟着技术论证。**先有论证，才有资格有态度。**

## 去 AI 味清单

写完逐条自查，命中就改：

**结构层**
- [ ] 开头有背景铺垫（"随着……的发展"、"在……场景中"、"众所周知"）→ 删掉，从第二段开始
- [ ] 结尾有"综上所述"、"总而言之"、"希望本文对你有帮助" → 删掉，最后一句应该是最后一个事实
- [ ] 每个小节都是"总起 - 展开 - 小结"三段式 → 小结删掉，读者不健忘
- [ ] 强行凑成三点、五点的排比 → 有几点写几点，两点就两点
- [ ] 通篇标题 + 加粗 + 列表，没有一段连贯的说理散文 → 复杂的因果推理必须用段落承载，列表装不下

**句子层**
- [ ] "值得注意的是"、"需要指出的是"、"不难看出"、无转折的"事实上" → 删掉，直接说事
- [ ] "首先……其次……最后……"当过渡词用 → 只在真有顺序时用
- [ ] 形容词堆砌："高效、稳定、可靠、易用、可扩展" → 换成一个数字或一个具体行为
- [ ] "赋能"、"抓手"、"闭环"、"链路"、"生态"、"深度融合"、"全方位" → 换人话
- [ ] 加粗超过全文 5% → 只加粗判据、结论、拒绝理由
- [ ] emoji、✅、🚀 → 全删
- [ ] 每句长度都差不多（30-40 字）→ 长短交替，结论句要短

**内容层**
- [ ] 有收益声称但没数字 → 补数字，补不了就删掉这句
- [ ] 只有 happy path，没有代价、边界、失败情况 → 补
- [ ] 说了"权衡"但没说权衡结果 → 给出你的选择和理由
- [ ] 提到替代方案却用"不适合我们的场景"打发 → 展开说清死在哪
- [ ] 全文没有一句读者能当场照做的话 → 加判据/公式/阈值

**最狠的一条**：把全文形容词和副词全部删掉，论证还站得住，说明骨架是硬的；一删就空了，说明本来就没东西可写。

## 场景适配

**技术文章 / 设计文档**：完整用十条。重点在规则 2（问题在前）、规则 7（NonGoals）、规则 8（对比方案）。

**周报 / 月报**：第一句给结论（做完了什么、卡在哪）。数字必须有。风险和没做的事要写。不要用"推进"、"跟进"、"对齐"这类没有终态的动词——写"完成"、"上线"、"被 X 阻塞"。

**故障复盘**：开头一句话定义现象，然后写**因果链**而不是时间流水账。时间线是证据，因果链才是结论。改进项必须带判据。

**方案评审**：把否决的方案和否决理由写进正文，这是评审时最省时间的部分。收益必须有数字，成本必须写全。

**PR 描述 / commit message**：第一句说清"改了什么、为什么"。已知局限写在正文里，别让 reviewer 自己发现。
